# Урок: «оболочка приклеивает кириллицу к имени переменной»

> Контекст: `start.command` — единственная точка входа стенда «НормаСтрой AI»
> для человека. Двойной щелчок, четыре шага, браузер. Сообщения человеку
> по-русски, имена переменных латиницей.

## Что произошло

Владелец запустил пусковой файл двойным щелчком. Три шага прошли, четвёртый
оборвался:

```
  1/4  Python 3.12.0 — /Library/.../python3.12
  2/4  прогон сторожей…
       22 passed in 3.04s
  3/4  пересборка указателя…
указатель пересобран: 11379 карточек из 75 файлов за 0.3 с
/Users/.../start.command: line 93: PORT?: unbound variable

[Процесс завершен]
```

Окно терминала закрылось (Finder добавляет `; exit;`), стенд не поднялся.

Строка 93 выглядела безобидно:

```bash
echo "  4/4  подъём страниц на порту $PORT…"
```

## Почему это случилось

**Многоточие «…» стоит вплотную к имени переменной, без пробела.** Это символ
U+2026, в UTF-8 — три байта `E2 80 A6`. Разбирая `$PORT…`, bash включил эти
байты в идентификатор и стал искать значение переменной с именем `PORT…`.
Её нет; `set -u` на неопределённой переменной обрывает работу.

В сообщении имя печатается как `PORT?` — терминал показывает нечитаемый байт
знаком вопроса, и из-за этого сообщение выглядит как опечатка в коде,
а не как склейка.

**Почему ловушка именно злая, а не просто досадная.** Ошибка не синтаксическая:
`bash -n` её не видит, потому что синтаксис верен. Она срабатывает только
при выполнении той самой строки — то есть на **последнем** шаге, после того
как человек увидел «22 passed» и «указатель пересобран». Обрыв на этом месте
читается как отказ изделия, а не как опечатка в пусковом файле.

Тот же механизм в другом виде уже ловил нас раньше:
[скобочный класс в shell совпадает с кириллицей](shell-bracket-class-matches-cyrillic.md).
Общее правило семьи: **оболочка и кириллица рядом ведут себя не так,
как читается глазами.**

## Как починили

Имя взято в скобки:

```bash
echo "  4/4  подъём страниц на порту ${PORT}…"
```

Скобки явно ограничивают идентификатор, и байты многоточия остаются текстом.

Заведены два сторожа — ни один из прежних двадцати двух поймать это не мог,
потому что ошибка жила в оболочке, а пакет проверял только код изделия:

```python
def test_puskovoy_fayl_razbiraetsya_obolochkoy():
    itog = subprocess.run(["bash", "-n", СТАРТЕР], capture_output=True, text=True)
    assert itog.returncode == 0

def test_imena_peremennyh_v_puskovom_fayle_otdeleny():
    """За $ИМЯ не должно стоять не-ASCII: пробел, кавычка и точка имя
    обрывают, а байты UTF-8 оболочка приклеивает к нему."""
    obrazec = re.compile(r"\$[A-Za-z_][A-Za-z_0-9]*([^\x00-\x7f])")
```

Второй сторож проверен красным на умышленно сломанном файле —
`assert not ['строка 107: …$PORT……']`. Проверку, которую не видели красной,
в пакет не кладут.

## Чтобы не повторилось

**Правило.** В пусковом файле, где сообщения человеку на русском, имя
переменной внутри строки пишется как `${ИМЯ}` — всегда, а не только там, где
кажется опасным. Разбирать глазами, где символ ASCII, а где нет, дороже,
чем поставить скобки везде.

**Что проверять на старте проекта с пусковым файлом:**

* `bash -n` на всех `.command`/`.sh` — в дымовой пакет, даже если файл
  «просто три строчки»;
* поиск `\$[A-Za-z_][A-Za-z_0-9]*[^\x00-\x7f]` по пусковым файлам;
* исполняемый бит: файл без него Finder открывает в редакторе, и человек
  решает, что изделие не поставилось.

**Что положить в чек-лист обзора кода.** Пусковой файл — часть изделия, а не
обвязка. Его правки просматриваются так же, как правки кода: именно он
формирует первое впечатление, и он же единственный, чей отказ человек
не отличит от отказа программы.

**Общий признак жанра.** Ошибка, которая срабатывает на последнем шаге длинной
последовательности, дороже такой же ошибки на первом: к четвёртому шагу человек
уже поверил, что всё исправно, и приписывает обрыв изделию. Шаги, которые
человек видит по одному, стоит проверять с конца.
