# Урок: «Запасной адрес стал исходящим: NAT не смотрит на src маршрута»

## Что произошло

Адрес VPN-сервера в РФ закрывали каждые трое суток. Чтобы не зависеть от смены адреса,
серверу назначили два плавающих IP (Hetzner Floating IP) — запасные входы, которыми до
блокировки никто не пользуется. Их не должен видеть ни один сайт, иначе их могут
«сдать» так же, как основной.

Адреса добавили через netplan, как в документации Hetzner. Сразу после этого:
- `curl https://api.ipify.org` **на самом сервере** — основной адрес, всё верно;
- тот же запрос **из контейнера VPN** и с ноутбука через туннель — **адрес запасного входа**.

Около 10 минут все сайты, куда семья ходила через VPN, видели запасной адрес. Его
заменили новым.

## Почему это случилось

- **netplan поставил статические адреса раньше DHCP.** После `netplan apply` порядок
  на eth0 стал «запасной 1, запасной 2, основной»: основной приходит по DHCP и
  добавляется последним.
- **MASQUERADE выбирает источник по интерфейсу, а не по маршруту.** В ядре это
  `inet_select_addr(out_dev, nexthop, RT_SCOPE_UNIVERSE)`: первый не-secondary адрес
  с глобальной областью, лучше из подсети шлюза. У всех адресов маска /32, шлюз
  Hetzner (172.31.1.1) не попадает ни в одну подсеть, и берётся просто первый
  в списке. `src` в маршруте по умолчанию (networkd ставит его для DHCP) действует
  только на пакеты самого хоста.
- **Проверили не там.** `ip route get` и `curl` на хосте показывают `src` маршрута,
  то есть правильный адрес. Ошибку видно только по ту сторону NAT: из контейнера или
  через туннель.

## Как починили

- **Дополнительным адресам — `Scope=link`.** `inet_select_addr` пропускает адреса,
  чья область уже глобальной, поэтому NAT их не выберет никогда. Принимать трафик они
  не мешают: Docker делает DNAT по `addrtype LOCAL`, а запись в локальной таблице
  маршрутов от scope не зависит. Проверено пробой: пакет на запасной адрес доходит
  до контейнера.
- **У netplan нет настройки scope**, поэтому адреса — в дополнении к конфигу
  systemd-networkd, которое netplan не трогает:
  `/etc/systemd/network/10-netplan-eth0.network.d/60-freeway-reserve.conf`

  ```ini
  [Address]
  Address=<запасной>/32
  Scope=link
  ```
- **`ip addr replace … scope link` у существующего адреса scope не меняет** — только
  удалить и добавить заново. При удалении адреса ядро само сбрасывает записи
  conntrack, которые NAT завязал на него, и новые соединения сразу идут с основного.
- Скрипт `~/FREEWAY/scripts/freeway-reserve` пишет это дополнение и проверяет, что
  netplan-конфиг eth0 не потерял DHCP и IPv6. Сеть он применяет с автооткатом через
  180 с, если нет подтверждения из новой SSH-сессии. `status` печатает «NAT source» —
  первый глобальный адрес eth0. Регрессионная проверка —
  `scripts/test_freeway_reserve.py::NatSource`.

## Чтобы не повторилось

- **После любого добавления адреса проверять исходящий IP с той стороны NAT**, откуда
  ходят клиенты: `docker exec <контейнер> wget -qO- https://api.ipify.org`, а не `curl`
  на хосте.
- **Дополнительный адрес, который не должен светиться, — только со `scope link`**
  (или явный SNAT на основной). Инструкция хостинга «добавьте /32 в netplan» верна для
  входящего трафика и молчит про исходящий.
- **Порядок адресов на интерфейсе ничего не гарантирует.** DHCP-адрес может встать
  последним после любого `netplan apply` или перезагрузки.
- **Рискованную смену сети на удалённом сервере — с автооткатом**
  (`systemd-run --on-active=180 … rollback`) и подтверждением из новой SSH-сессии:
  старая сессия может пережить то, после чего новая уже не войдёт.
