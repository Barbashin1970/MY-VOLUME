Объект — библиотека AirLLM на macOS (ветка MLX, коммит `c6f3ec0` из main). Цель — проверить,
даёт ли AirLLM на ноутбуке с 16 ГБ памяти практическую возможность запускать модели больше
памяти, и сравнить его с уже используемой Ollama. Метод — сверка заявлений из видео
с первоисточниками (README, PyPI, issues, исходный текст) и сравнительный замер на одной
модели и одном промпте с заранее известным эталоном ответа.

Получено: AirLLM на Mac работает (TinyLlama 1.1B, ответ верный, 3,82 с на токен), но на
Llama 3.1 8B выдаёт 22,35 с на токен против 0,061 с у Ollama — медленнее в ≈366 раз; пик
памяти процесса — 14,5 ГБ из 16; ответ на контрольный вопрос неверный, тогда как Ollama
на тех же весах в 4-битном виде отвечает верно. Сценарий «70B на слабом ноутбуке» на этом
стенде невозможен: модель весит 141,1 ГБ при 68 ГБ свободного диска.

Область применения — выбор способа запуска локальных моделей на ноутбуках Apple с 16 ГБ.
Рекомендация: локальные модели — через Ollama, 7–8B в 4 битах; AirLLM на Apple Silicon
не использовать.

## ТЕРМИНЫ И СОКРАЩЕНИЯ

- **Послойная загрузка** (layer-wise inference) — способ AirLLM: в память поднимается один
  слой модели, вычисляется и выгружается; на каждый новый токен — заново все слои.
- **Квантизация Q4_K_M** — хранение весов примерно 4,5 бита на вес (формат GGUF, Ollama).
- **bf16** — 16 бит на вес, без сжатия; так модель лежит на Hugging Face.
- **MLX** — библиотека Apple для вычислений на GPU Apple Silicon; через неё AirLLM работает на Mac.
- **`rope_theta`, `rope_scaling`** — параметры позиционного кодирования RoPE. У Llama 3.1
  `rope_theta` = 500000 и `rope_scaling` типа `llama3` с множителем 8; у TinyLlama — 10000 и нет.
- **Пиковая память** — строка `peak memory footprint` в выводе `/usr/bin/time -l`.
- **Своп** — файл подкачки macOS.

## 1. ВВЕДЕНИЕ

**Актуальность.** В коротких видео (октябрь–ноябрь 2026) советуют `pip install airllm`,
чтобы запускать «Llama 3 • DeepSeek • Mistral • Kimi» на слабом ноутбуке. У исполнителя
MacBook Air M2 16 ГБ, и локальная языковая модель уже работает через Ollama: она по умолчанию
используется в [РАГРАФ](../../projects/active/ragraf/README.md). Нужно решить, есть ли смысл
переходить. Второй совет из того же набора — API Anything (сайт как API для агентов) —
к локальным моделям не относится и в опыт не вошёл: его установка меняет конфиги агентов,
решено отложить.

**Цель.** Проверить, даёт ли AirLLM на этом ноутбуке практическую возможность запускать
модели больше памяти, и сравнить его с Ollama.

**Задачи.**

- З1. Сверить заявления из видео с первоисточниками.
- З2. Определить, применим ли сценарий «70B на слабом ноутбуке» к этому стенду.
- З3. Проверить, работает ли AirLLM на Mac вообще (малая модель).
- З4. Сравнить AirLLM и Ollama на одной модели и одном промпте: скорость, память, качество.
- З5. Дать рекомендацию по локальным моделям для этого ноутбука и для РАГРАФ.

**Объект и предмет.** Объект — AirLLM на macOS. Предмет — скорость генерации, пиковая память
и правильность ответа в сравнении с Ollama.

**Ожидание до опыта** (записано в переписке до замеров): AirLLM запустится на малой модели;
на Llama 3.1 8B даст 5–10 с на токен против ~13 токенов в секунду у Ollama; 70B на этом
ноутбуке не поместится на диск.

- **Опыт:** полный текст заметки

- **Эталон ответа известен заранее:** (1) двойной префикс пути `/api/v1/api/tasks` → 404;

- Шаблон чата применён в обоих инструментах (`apply_chat_template` и `/api/chat`).

| Величина | Как определена |

Параметры: temperature 0, не более 50 новых токенов, остановка на токене конца ответа;
у Ollama `num_ctx` 8192 и `keep_alive` 0. Замеры шли поочерёдно, не одновременно.
**По одному прогону на конфигурацию — разброс между прогонами не оценён.**

### 3.4. Условия

Полностью не контролировались. Работали VS Code (7 окон), Claude Code, VPN-клиент.
По решению владельца до прогона 8B закрыты GigaCode (8 процессов `gigacode serve`, около
2 ГБ) и Google Chrome (около 3,5 ГБ). Служба `fseventsd` держала 7,8 ГБ, почти всё в свопе,
после 11 дней без перезагрузки. Во время прогона AirLLM 8B уровень нехватки памяти был 2,
«предупреждение» (`sysctl kern.memorystatus_vm_pressure_level`), своп вырос с 9,0 до 13,6 ГБ
(`sysctl vm.swapusage`). Перед прогонами Ollama — уровень 1, «норма». Тепловое снижение
частот на ноутбуке без вентилятора не контролировалось.

## 5. ОБСУЖДЕНИЕ И ГРАНИЦЫ ПРИМЕНИМОСТИ

**Почему медленно.** На каждый токен заново читаются все 35 частей модели — эмбеддинги,
32 слоя, нормализация и выходной слой. Это 16,1 ГБ на токен; при 22,35 с выходит около
0,72 ГБ/с вместе с разбором весов. Скорость SSD отдельно не мерилась.

**Почему не экономит память.** Пик 14,5 ГБ при заявленном смысле метода «один слой
в памяти». Предположение: освобождённые буферы оседают в кэше MLX — в коде нет вызовов
его очистки. Не проверялось. Именно этот рост загнал систему в своп (раздел 3.4).

**Почему ответ неверный.** Ollama на тех же весах отвечает верно, значит, дело не в модели.
Кандидаты: `rope_scaling` типа `llama3` не передаётся в RoPE (раздел 2); различие шаблонов
чата (25 токенов). Причинная связь не доказана: нужен повтор с учтённым `rope_scaling`
или с моделью без него на том же длинном промпте.

**Почему смоук этого не поймал.** У TinyLlama нет `rope_scaling`, а `rope_theta` = 10000 —
ровно тот случай, где оба известных дефекта пути MLX не проявляются. Зелёная проверка
на малой модели не доказала пригодность для настоящей (навык `otbor-proverok`:
«зелёный набор ничего не доказывает»).

**Что получено нового** (сделано — в отличие от — проверено — ограничение):

- замерено: AirLLM на Apple Silicon с Llama 3.1 8B — 22,35 с на токен и пик 14,5 ГБ;
  в отличие от README, где есть только объёмы видеопамяти для NVIDIA; проверено одним
  прогоном на MacBook Air M2 16 ГБ; без повторов и при неконтролируемой фоновой нагрузке;
- обнаружено: путь MLX не учитывает `rope_scaling`, и на длинном промпте ответ неверен
  при верном ответе Ollama на тех же весах; причинность не доказана, issue в AirLLM
  не заведён.

**Границы.** Один ноутбук, один промпт, одна пара моделей, по одному прогону. Память Ollama
и время скачивания для Ollama не мерились. Сжатие AirLLM (`compression`, через bitsandbytes)
и работа на CUDA не проверялись — выводы относятся только к macOS и MLX.
