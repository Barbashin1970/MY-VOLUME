# Урок: «репозиторий приватный, а `/README.md` публичный»

> Контекст: визитка Платформы АРХИ — статический сайт в корне репозитория,
> публикуется на Vercel. Репозиторий приватный, и это создавало ложное
> чувство, что внутренние заметки защищены. Поймано на предпубликационном
> обзоре, до того как ссылка ушла партнёру.

## Что произошло

В `.vercelignore` лежало:

```
ishodniki-kartinok/
*.md
!README.md
```

Третья строка написана из привычки к `.gitignore`, где отрицание —
обычный приём «исключить всё, кроме одного». Здесь она означала:
**README едет наверх вместе с сайтом**.

Сайт статический, каталог вывода — корень репозитория. Значит всё, что
уехало, отдаётся по своему адресу. README уходил по `/README.md` — а в нём
был порядок публикации, имена переменных окружения и абзац «это данные
Группы МЕТА и Айбим, и права публиковать их у нас нет». Документ,
написанный про партнёра, лежал бы в открытом доступе на странице,
адресованной этому партнёру.

## Почему это случилось

**Два рубежа перепутаны местами.** «Репозиторий приватный» и «деплой
приватный» — разные вещи, и второе из первого не следует. Приватность
репозитория закрывает `github.com/<кто>/<что>`, а хостинг отдаёт ровно
то, что ему выгрузили, по публичному адресу. Между ними нет никакой связи,
кроме той, что мы сами достраиваем в голове.

**Синтаксис совпадает, а назначение разное.** `.vercelignore` повторяет
синтаксис `.gitignore`, включая отрицание, — и рука пишет `!README.md`
автоматически. Но `.gitignore` решает «что коммитить», а `.vercelignore` —
«что показывать миру». Одинаковая запись, противоположная цена ошибки.

**Ошибка невидима в обычной работе.** Никто не ходит на `/README.md`
руками. Файл лежит и ждёт поисковый обход или любопытного, а на сайте
ничего не ломается — поэтому ни один функциональный тест его не поймает.

## Как починили

Отрицание убрано, ignore-файл дополнен и снабжён объяснением, чтобы
следующий раз никто не «починил» его обратно:

```
# README.md ОСТАЁТСЯ ВНИЗУ НАМЕРЕННО. Сайт статический, каталог вывода —
# корень, поэтому всё, что уехало, отдаётся по своему адресу.
ishodniki-kartinok/
*.md
obnovit-iz-izdeliya.sh
.DS_Store
.vercel
```

## Чтобы не повторилось

**Правило 1. Отрицание в `.vercelignore` — почти всегда ошибка.** Если
тянет написать `!файл`, спроси: «я хочу, чтобы этот файл открывался
по своему адресу в интернете?». Обычно ответ «нет», и тогда отрицание
не нужно вовсе.

**Правило 2. У статического деплоя нет «служебных» файлов.** Всё, что
лежит в каталоге вывода, — публичная страница. `README.md`, `*.sh`,
`*.sql`, `notes.txt`, `.env.example` — каждый отдаётся по своему пути.
Единственная защита — не выгружать.

**Правило 3. Проверять ответом сервера, а не списком файлов.** Глазами
по `.vercelignore` ошибка не видна — она видна только запросом. В список
проверок после деплоя идёт строка, где перечислено то, чего быть не должно:

```bash
S=https://<проект>.vercel.app
for p in /README.md /package.json /.env /obnovit-iz-izdeliya.sh; do
  printf "%-28s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' "$S$p")"
done   # каждая строка обязана дать 404
```

**Правило 4. Проверка обязана смотреть обе стороны.** «Живое отдаёт 200»
ловит половину бед. Вторая половина — «лишнее отдаёт 404», и без неё
утечки этого жанра не находятся никогда.

**Правило 5. Внутреннее — в другое место, а не в тот же каталог.**
Надёжнее ignore-файла то, что физически не лежит в каталоге деплоя.
Стратегия, оценка прав, переписка с заказчиком — в vault или в соседнюю
папку, а не рядом с `index.html`.
