# JTBD — Jobs To Be Done

**«Клиент нанимает продукт для решения своих задач».** Подход Тони
Ульвика и Клейтона Кристенсена: не «кто наш клиент демографически»,
а «какую работу (job) клиент пытается выполнить, и какой продукт он
нанимает для этого».

## Главная формула

> **«Когда _\<ситуация\>_, я хочу _\<motivation/desired progress\>_, чтобы _\<expected outcome\>_».**

Пример: «Когда я добираюсь на работу утром в плотном трафике, я хочу
не нервничать и продуктивно использовать время, чтобы прийти в офис
спокойным и подготовленным» → клиент нанимает не «такси», а «удобную
дорогу + рабочее время в пути».

## Когда применять (vs альтернативы)

| Подход | Когда выбирать | Главный артефакт |
|--------|----------------|------------------|
| **JTBD** | Не понимаешь, **зачем** клиент покупает | JTBD-интервью |
| **Дизайн-мышление** | Не понимаешь, **что** клиент чувствует (эмпатия) | Customer Journey + Empathy map |
| **4 шага Стива Бланка (МРП)** | Стартап, нужна последовательность Customer Discovery → Validation → Creation → Scaling | Гипотезы о клиенте/проблеме |
| **Проблемное интервью** | Хочешь подтвердить **существование** боли | Скрипт проблемного интервью |
| **Глубинное интервью** | Хочешь понять **глубинные мотивы** | Скрипт глубинного интервью |

**Важно:** три типа интервью **конкурируют** — с одним респондентом
проводишь только один из них. См. [product-focus](product-focus.md) §4.

## Главные инструменты JTBD

1. **JTBD-интервью** — структурированный опрос: «когда вы в последний
   раз купили _X_, что произошло до этого момента?». Reverse-timeline
   от покупки к триггеру.
2. **JTBD-сегментация** — деление клиентов по **типу работы (job)**,
   а не по демографии.
3. **JTBD-приоритизация** — ранжирование jobs по «важности + неудовлетворённости».

## Дополняемое (не конкурент)

JTBD не покрывает:
- **Карту стейкхолдеров** — бери из Дизайн-мышления.
- **«Наблюдение»** — бери из Дизайн-мышления (или этнографии).
- **«Спросите маму»** — правила интервью Роба Фитцпатрика, применимы
  поверх любого типа интервью (не задавать ведущих вопросов, говорить
  про прошлое поведение, не питчить).

Можно смешивать. См. пример таблицы «PF структура с JTBD как моделью»
в [product-focus](product-focus.md).

## Применение в твоих проектах

| Проект | Job клиента (гипотеза) |
|--------|-----------------------|
| **AI-SKLAD** | «Когда я каждое утро разбираю остатки в Excel, я хочу за 15 минут вместо 2 часов получить готовый список действий, чтобы успеть к 11:00 раздать задачи менеджерам». |
| **LEYKA** | «Когда я как руководитель проекта в НГУ перевожу задачу в done, я хочу чтобы это автоматически попало в годовой отчёт по КОСГУ, чтобы не собирать ручную сводку в декабре». |
| **RAGRAF** | «Когда у меня сработал датчик IoT, я хочу чтобы регламент автоматически создал задачу нужному человеку в LEYKA с фактической проверкой исполнения через тот же датчик». |
| **SOFIA** | «Когда я задумываюсь о своём психо-эмоциональном состоянии, я хочу получить персональный рецепт эфирных масел на основе моей даты рождения, чтобы попробовать ароматерапию системно». |

## Когда **не** применять

- **MVP уже есть, продукт продаётся** — переходи к Kano / RICE приоритизации
  существующих фич.
- **B2G заказчик с готовым ТЗ** — JTBD клиента известен, но решение
  диктуется заказчиком. Применяй ограниченно для конечного пользователя.
- **Технический инструмент для разработчиков** (POLINOM) — JTBD = «не
  ломать архитектуру под нагрузкой». Слабее работает.
