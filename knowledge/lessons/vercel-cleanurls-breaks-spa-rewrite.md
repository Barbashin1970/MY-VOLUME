# Урок: «cleanUrls + SPA-rewrite = 404 на прямых ссылках»

> Контекст: у РАГРАФа есть отдельная landing-сборка на Vercel. Добавили вторую
> посадочную страницу `/archi`. Ссылка в подвале работала, прямая ссылка —
> 404. Потратили три итерации деплоя, из них две — на неверную диагностику.

## Что произошло

Симптом обманчивый и очень характерный для SPA:

- переход на `/archi` **по ссылке внутри приложения** — работает;
- **прямой заход** по `https://site.vercel.app/archi` (адресная строка,
  внешняя ссылка, обновление страницы) — `404`, заголовок
  `x-vercel-error: NOT_FOUND`;
- корень `/` при этом отдаёт 200 и всё работает.

Разное поведение потому, что это два разных механизма: переход по ссылке
обрабатывает клиентский роутер в уже загруженном приложении, а прямой заход
идёт на сервер, где файла `archi` нет — в сборке лежит один `index.html`.

## Почему это случилось

Две наложившиеся причины, обе про `vercel.json`.

**1. `source` у Vercel — это path-to-regexp, а не обычное регулярное выражение.**
Первая попытка исключить ассеты отрицательным просмотром вперёд:

```json
{ "source": "/((?!assets/|.*\\.[a-zA-Z0-9]+$).*)", "destination": "/index.html" }
```

не совпала ни с одним адресом, и правило молча не сработало. Исключать ассеты
вручную **не нужно**: Vercel сначала ищет реальный файл на диске и только потом
применяет `rewrites`, поэтому статика не перехватывается.

**2. Главная причина — `"cleanUrls": true` в паре с назначением `/index.html`.**
`cleanUrls` объявляет `/index.html` неканоническим адресом и вешает на него
редирект `308 → /`. Переадресация, чьё назначение — `/index.html`, упирается в
путь, который в таблице маршрутов больше не отдаёт файл, а редиректит; запрос
проваливается в 404. Для одностраничного приложения с единственным HTML-файлом
`cleanUrls` не даёт ничего.

## Как починили

`frontend/vercel.json` — убрать `cleanUrls`, оставить каноничную конфигурацию:

```json
{
  "buildCommand": "npm ci && npm run build:landing",
  "outputDirectory": "dist-landing",
  "framework": null,
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
```

Вторая половина починки — на стороне приложения: в landing-сборке вообще не было
`<Routes>`, монтировался только главный экран. Поэтому даже с рабочей
переадресацией `/archi` показывал бы главную. Добавили маршруты с ленивой
загрузкой и `<Route path="*">` на возврат к корню.

## Чтобы не повторилось

**Правило 1. Признак «ссылка работает, прямой заход — 404» = нет серверной
переадресации.** Это всегда про хостинг, а не про код роутера. Проверять сразу
после первого деплоя SPA, а не когда заметит заказчик.

**Правило 2. Для SPA на Vercel — ровно одна строка, без изобретательности:**
`{"source": "/(.*)", "destination": "/index.html"}`. Ассеты исключать не надо,
`cleanUrls` не включать.

> ⚠️ **Срок годности у этого правила есть.** Оно верно, пока задача — «чтобы
> сайт открывался». Как только сайт начинают индексировать, эта же строка
> становится вредной: она отвечает 200 на любой несуществующий адрес, и
> поиск считает это мягким 404. Перед публикацией шаблон меняется на
> точечные правила плюс `404.html` — см.
> [spa-catchall-rewrite-is-a-soft-404.md](spa-catchall-rewrite-is-a-soft-404.md)
> (БЕРИМАЖ, 2026-09-09).

**Правило 3. Как проверить, читается ли `vercel.json` вообще.** Смотреть надо на
эффект, которого не может быть по умолчанию:

- ❌ **неверно:** `cache-control: immutable` на ассете — Vercel ставит его
  хешированным файлам сам, конфиг тут ни при чём. На этом я потерял итерацию,
  сделав ложный вывод «конфиг читается»;
- ✅ **верно:** запросить путь, поведение которого задаёт именно конфиг. Например
  при `cleanUrls: true` запрос `/index.html` обязан вернуть `308` с `location: /`.
  Ещё надёжнее — временно добавить свой заголовок в блок `headers` и проверить его.

**Правило 4. Проверять маршруты пачкой, а не по одному.** Одна команда ловит
и регрессии соседних страниц (у нас так же молча не открывались `/investors`,
`/consulting`, `/yandex-tracker`):

```bash
for p in / /archi /investors /consulting; do
  printf "%-16s → %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' https://site.vercel.app$p)"
done
```

**Правило 5. Если правка конфига «не помогла» — сначала докажи, что она
задеплоена.** При изменении только `vercel.json` хеш JS-бандла не меняется, и по
нему свежесть деплоя не определить. Признак живой переадресации — любой
заведомо несуществующий адрес (`/nonexistent-xyz`) отдаёт `200`, а не `404`.

> ⚠️ Этот признак работает только при сплошном шаблоне. После перехода на
> точечные правила он переворачивается: несуществующий адрес обязан отдавать
> `404`, и «200» становится симптомом беды, а не здоровья. Тогда свежесть
> деплоя проверяют иначе — по адресу, поведение которого задаёт именно новый
> конфиг (например, `/podbor/` со слэшем обязан вернуть `308`).

**Правило 6. Отдельная landing-сборка — отдельный набор маршрутов.** Если у
проекта две точки входа (полное приложение и урезанный лендинг), добавление
страницы требует правки обеих. И ссылки на разделы, которых в урезанной сборке
нет, должны уходить наружу на полный экземпляр, а не в никуда.
