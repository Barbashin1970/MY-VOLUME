# Урок: «IP заблокировали — меняем адрес по токену, а не чиним сервер»

## Что произошло

2026-10-25 около 17:10–17:20 (+07) у всех устройств семьи перестал подключаться
VPN (AmneziaWG, сервер Hetzner, Германия). Отказ был одновременным, у трёх разных
провайдеров: домашний, мобильный и ещё один домашний. Одно устройство при этом
продолжало работать. В тот же день пришло письмо Hetzner про уязвимости в PHP,
а на их странице статуса висели инциденты с метриками. Первая мысль: Hetzner
остановил серверы или нас взломали.

На деле сервер работал 46 дней без перезагрузки, контейнер VPN не перезапускался.
PHP на сервере нет вовсе. Все входы root сделаны нашим единственным ключом.

## Почему это случилось

- **Российская сторона (ТСПУ) закрыла конкретный IP сервера.** Новые соединения
  к нему по TCP и UDP не доходили ни на одном порту, даже SSH. Другой IP того же
  Hetzner из той же сети открывался.
- **Уже открытый UDP-поток жил дальше**, даже через перезагрузку сервера. Клиент
  не менял исходный порт, и фильтр считал это тем же потоком. Отсюда «одно
  устройство работает», что сбивает с толку.
- **Письмо про PHP и инциденты метрик Hetzner — совпадение по времени, а не причина.**

## Как нашли

1. **Учёт по ключам** (сборщик раз в минуту на сервере): все устройства пропали
   в одни и те же 10 минут, у разных провайдеров.
2. **Захват на сервере** (`tcpdump udp port 41259`): от «отвалившихся» устройств
   не приходит ничего, даже попыток рукопожатия.
3. **Проверка пути в обход включённого VPN.** На Mac работал сторонний VPN.
   Переключать его на наш неработающий туннель нельзя: весь трафик ушёл бы в тупик,
   и оборвалась бы своя же сессия. Вместо этого сокет привязали к физическому
   интерфейсу (`IP_BOUND_IF = 25`, `en0`). Через `en0` ya.ru, 1.1.1.1 и другой IP Hetzner
   соединяются, а наш IP даёт тайм-аут на всех портах, и в `tcpdump` на сервере пусто.
   Это блокировка адреса по дороге.

## Как починили — по токену, около минуты простоя

Подготовка (один раз):
- **Токен.** Hetzner Cloud Console → проект → Security → API Tokens, права
  **Read & Write**. В чат не вставлять: скопировать и выполнить
  `pbpaste > ~/.config/hcloud/freeway-token && chmod 600 …`.
- **Проверить, что смена адреса ничего не сломает.**
  - IPv4 приходит по DHCP (`dhcp4: true` в netplan — по умолчанию у Hetzner).
  - Старый IP нигде не вшит: `grep -r` по `/etc`, конфигам контейнера и правилам
    iptables. NAT у Amnezia — `MASQUERADE`, он сам подхватит новый адрес.
  - Пиры сохранены: `awg show peers` совпадает с `awg0.conf`. У контейнера `restart: always`.

Сама смена (`~/FREEWAY/scripts/`):

```bash
scripts/hz-swap-ip status            # только чтение: сервер, его адреса, все Primary IP
scripts/hz-swap-ip swap              # выключить → снять старый (auto_delete off, не удалять)
                                     # → создать и назначить новый → включить; при сбое — назад
ssh-keyscan -t ed25519 <NEW> | ssh-keygen -lf -   # ключ хоста = прежний, иначе стоп
scripts/probe-path <NEW>             # из дома в обход VPN + tcpdump на сервере
scripts/hz-swap-ip delete-ip <old>   # старый — удалить, когда всё работает
```

Замер 2026-10-26: смена через API — 35 с, затем сервер поднялся с новым адресом по
DHCP. Всего около минуты. После смены:
- в панели (Railway): `SSH_HOST` и строка `Endpoint` в `AWG_CLIENT_TEMPLATE`;
- на устройствах: Endpoint в AmneziaWG;
- в vpn://-ссылках «Ульты Лайт»: заменить IP внутри сжатого JSON (4 байта длины
  + zlib, base64url) и проверить, что ссылка распаковывается обратно.

Грабли API (2026): у сервера нет поля `datacenter`, теперь `location`. Python
с python.org на macOS не доверяет сертификатам, нужен `cafile=/etc/ssl/cert.pem`
([урок](python-org-macos-urllib-no-root-certificates.md)). У старого IP стоял
`auto_delete: true`, его выключили до снятия адреса, чтобы откат был гарантирован.

## Оценка: Floating IP вместо смены основного

Цены — по [документации Hetzner](https://docs.hetzner.com/general/infrastructure-and-availability/ipv4-pricing),
устройство — по [FAQ Floating IP](https://docs.hetzner.com/cloud/floating-ips/faq/).

| | Смена основного IP (сделали) | Floating IP |
|---|---|---|
| Цена IPv4 | €0,50/мес (без НДС) | €3,00/мес (€3,57 с НДС) **сверх** основного |
| Простой при смене | ~1 мин: сервер выключается | нет: переназначить адрес и прописать его в ОС |
| Настройка в ОС | никакой, адрес приходит по DHCP | вручную: netplan, `addresses: [<ip>/32]` — DHCP его не выдаёт; при каждой смене правка и `netplan apply` |
| SSH и панель | переезжают на новый адрес, нужно править `SSH_HOST` | остаются на основном адресе: из-за рубежа он доступен, панель не трогаем |
| Исходящий трафик клиентов | с нового адреса | по умолчанию с **основного**, заблокированного адреса (так выбирает источник Linux; в документации Hetzner об этом нет — проверять). Если блок двусторонний, российские сайты через VPN могут не открываться; лечится SNAT на плавающий адрес |
| Запас | новый адрес создаётся за секунды | можно заранее держать проверенный из РФ «тёплый» адрес; до 10 штук на аккаунт |
| Где работает | в своей локации | в пределах сетевой зоны (eu-central: fsn1, nbg1, hel1) |

**Вывод.** Для семейного VPN с редкими блокировками смена основного IP по токену
дешевле и проще: одна команда и минута простоя. Floating IP окупается, когда:
- блокировки стали частыми (раз в неделю и чаще);
- простой недопустим;
- хочется не трогать панель и SSH;
- нужен заранее проверенный запасной адрес для мгновенного переключения.

В обоих случаях устройства всё равно надо перенастраивать на новый Endpoint.
Это снимает только **адрес по имени (DNS)** — бэклог FREEWAY № 5.

## Как адрес мог попасть в список (гипотезы, по убыванию веса)

Точной причины РКН не сообщает. Блок закрыл адрес целиком, все порты, поэтому
похоже на внесение IP в список, а не на фильтр протокола.

1. **Российские приложения внутри полного туннеля.** При `AllowedIPs = 0.0.0.0/0`
   VK, MAX, «Госуслуги» и банки видят адрес сервера как адрес пользователя.
   По расследованию InterSecLab, MAX при каждом запуске сообщает VK IP устройства
   и признак VPN ([Настоящее Время](https://www.currenttime.tv/a/v-max-optsiya-dlya-slezhki-za-polzovatelyami/33863745.html)).
   Получается иностранный адрес хостинга, за которым сидят несколько российских
   аккаунтов с пометкой «VPN», — готовая улика.
2. **`.conf` пересылали через MAX.** В конфиге всё сразу: IP и порт сервера, ключи,
   PSK и параметры маскировки. Сквозного шифрования у MAX, по разборам, нет,
   данные доступны ФСБ по требованию ([The Moscow Times](https://ru.themoscowtimes.com/2026/09/29/peredaet-dannie-fsb-gosmessendzher-max-nachal-sledit-za-laikami-i-kommentariyami-rossiyan-a207328)).
   Шаблон WireGuard-конфига (`[Interface]`, `PrivateKey`, `Endpoint`) находится
   автоматически.
3. **Лишние прокси на том же IP** (Reality под microsoft.com, MTProto, Shadowsocks).
   Сканеры проверяли их сотнями раз. Мобильные сети пометили адрес через две недели
   после их запуска.
4. **Узнаваемый рисунок AmneziaWG v2.** Пакет `I1` — DNS-запрос к icloud.com,
   но идёт он на порт VPN, а не на 53. Плюс постоянный набор «мусорных» пакетов
   перед рукопожатием.

Утечку ключей проверили по истории подключений. С 21.10 все адреса ключей
принадлежали известным провайдерам семьи (МТС, Дом.ру, НГУ), посторонних нет.

## Чтобы не повторилось

- **Конфиги не пересылать через мессенджеры, и особенно через MAX.** Только AirDrop
  или QR при встрече. Утёкший ключ отзывать и выдавать новый.
- **Российские сервисы — мимо туннеля.** Раздельное туннелирование: исключить
  российские сети из `AllowedIPs`, на Android — исключить приложения MAX, «Госуслуги»
  и банки. Иначе адрес сервера сам «представляется» им при каждом входе.

- **Сначала путь, потом сервер.** Если сервер жив, а пакеты до него не доходят
  (`probe-path` в обход VPN плюс `tcpdump` на сервере), это блокировка адреса.
  Её лечит только новый адрес, правки сервера и протокола не помогут.
- **Отличать блок адреса от блока протокола.** Если до IP доходят обычные TCP и UDP,
  а рукопожатие VPN нет, режут протокол: менять маскировку (параметры AmneziaWG),
  а не IP.
- **Держать наготове токен (файл 600) и скрипт смены.** Тогда смена занимает
  минуту, а не вечер, и делается без консоли.
- **Новый адрес из пула проверять до раздачи клиентам.** Его могли закрыть ещё
  у прежнего владельца.
- **Меньше примет на VPN-адресе.** Лишние прокси (mtg, xray) никто из своих
  не использовал, а сканеры (Censys и т. п.) проверяли их сотнями раз — выключили.
- **Письмо хостера и инцидент на его статусе — повод проверить, а не объяснение.**
  Сверять время: блок начался за сутки до инцидента с метриками.

## Что было дальше (2026-10-28 — 2026-11-01)

- **Новые адреса закрывали через двое-трое суток:** 25.10, 28.10 и 31.10, каждый раз
  около 10:00 UTC (17:00 в Новосибирске). Смена параметров маскировки 28.10 не помогла.
  Значит, дело не в рисунке протокола, а в том, как адрес попадает в список.
- **Закрытые адреса не размораживают,** по крайней мере за неделю. 01.11 все три
  старых адреса закрыты, включая сданные обратно в пул Hetzner. Проверка трассировкой,
  не касаясь адреса: [vpn-outage-forensics](../skills/vpn-outage-forensics.md), шаг 6б.
- **Сработал вывод «Floating IP окупается при частых блокировках».** Серверу назначены
  два запасных плавающих IP, которыми никто не пользуется до блокировки (идея Олега).
  При блокировке меняется только адрес в клиенте: сервер не выключается, панель и SSH
  остаются на основном адресе, его блокировка в РФ им не мешает. Грабли этого шага —
  [masquerade-picks-floating-ip-as-source](masquerade-picks-floating-ip-as-source.md):
  запасной адрес чуть не стал исходящим для всех.
