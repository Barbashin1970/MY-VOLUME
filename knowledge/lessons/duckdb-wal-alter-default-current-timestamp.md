# Урок: «база живёт в журнале, а журнал не проигрывается»

> Контекст: РАГРАФ, FastAPI + встроенная DuckDB 1.5.2, один файл базы на
> экземпляр. Подготовка базы при старте: `CREATE TABLE` с исходными столбцами,
> затем десятки `ALTER TABLE … ADD COLUMN` — идемпотентная миграция схемы.

## Что произошло

На ноутбуке с Windows при старте сервера:
`WAL corruption detected; rotating regulations.duckdb.wal → …corrupted-<метка>`,
затем `seeded 65 new regulation(s) from fixtures` и все миграции заново.
База собралась из поставки 06.11 и снова 07.11.2026. Работа пользователя
осталась в отложенных журналах, каждый старт шёл долго: засев, миграции,
векторы документов. На Mac разработчика этого не видно никогда.

## Почему это случилось

Опыты на Mac, DuckDB 1.5.2: свежий файл, команды, снятие процесса без
остановки (`os._exit`), повторное открытие.

| Команда в журнале | Проигрывается? |
|---|---|
| `CREATE TABLE … DEFAULT CURRENT_TIMESTAMP` | да |
| `ALTER … ADD COLUMN … DEFAULT FALSE`, `CREATE INDEX` | да |
| `ALTER … ADD COLUMN ts TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | **нет** |
| `ALTER TABLE t ADD COLUMN x VARCHAR`, если у `t` уже есть столбец `DEFAULT CURRENT_TIMESTAMP` | **нет** — даже с CHECKPOINT между `CREATE` и `ALTER` |

Отказ: `INTERNAL Error: Failure while replaying WAL file …: Calling
DatabaseManager::GetDefaultDatabase with no default database set`.

Три условия сложились вместе:
1. **Схема** — `ALTER` над таблицей со значением по умолчанию `CURRENT_TIMESTAMP`.
   Видимо, при проигрывании `ALTER` DuckDB заново разбирает значения по умолчанию
   таблицы, а базы по умолчанию в этот момент ещё нет.
2. **CHECKPOINT был только на штатной остановке.** До первой остановки вся база —
   основной файл 12 КБ, журнал 1,9 МБ.
3. **На Windows сервер не останавливают штатно:** закрывают окно крестиком,
   `Stop-Process`, `taskkill /F`. Код восстановления «отложить битый журнал
   и открыть заново» честно отрабатывал — и база оказывалась пустой.

Эту ошибку уже видели на Railway и закрыли CHECKPOINT на остановке. Снятие
процесса защиты не получило.

## Как починили

- CHECKPOINT обеих баз **в конце подъёма приложения** — после схемы, миграций и
  засева, перед `yield` в lifespan. Опыт: после него снятый процесс базу не теряет,
  а последующие `INSERT` и `UPDATE` проигрываются нормально.
- CHECKPOINT **по расписанию**, раз в 10 минут: граница потери для того, что
  сделано после подъёма. Сбой CHECKPOINT печатается и не повторяется сразу.
- Проверка повторяет опыт: свежий каталог → настоящий подъём в отдельном процессе →
  `os._exit` → база открывается со всеми регламентами.

Файлы: `backend/app/services/sohranenie_bazy.py`, `backend/app/main.py`,
`backend/tests/test_sohranenie_bazy.py`; разбор — `docs/ZAPUSK-WINDOWS-RAZBOR.md`, п. 11.

## Как восстановить отложенный журнал (дополнено 2026-11-07)

Журнал, который при прямом открытии падает с «GetDefaultDatabase», **проигрывается
штатной DuckDB 1.5.2 через `ATTACH` из соединения в памяти**: база по умолчанию
(«memory») тогда уже задана.

```python
import duckdb
duckdb.connect("vosst.duckdb").close()      # 1. сначала пустой файл базы
# 2. потом рядом — копия журнала под именем vosst.duckdb.wal
c = duckdb.connect()                         # 3. соединение в памяти
c.execute("ATTACH 'vosst.duckdb' AS r")      #    журнал проигрывается
c.execute("CHECKPOINT r"); c.execute("DETACH r")  # и переносится в файл
```

- **Порядок важен.** DuckDB, создавая новый файл базы, выбрасывает лежащий рядом
  журнал — пустой файл создаётся раньше, чем кладётся журнал.
- **Пустой основной файл годится**, если журнал начат с пустой базы: его первая
  запись — `CREATE TABLE …`. Журнал от другой базы DuckDB тоже принимает и
  проигрывает: проверки «журнал от этого файла» нет.
- **Оборванный хвост журнала** DuckDB отбрасывает сам и открывает базу.
- Так 2026-11-07 проиграны оба журнала с ноутбука РАГРАФ (2 и 11 МБ): по 65
  регламентов. Ручной работы в них не оказалось — но узнать это можно было только
  проиграв их.

**В изделии РАГРАФ это теперь делает сама служба.** Если прямое открытие
падает на журнале, она сначала проигрывает его через `ATTACH` и лишь затем
откладывает (`backend/app/services/sohranenie_bazy.py`, `proigrat_zhurnal`;
перед попыткой снимается копия журнала).

## Чтобы не повторилось

- **Встроенная база с журналом — после каждой миграции схемы CHECKPOINT,** не только
  на штатной остановке. Остановку на Windows, в контейнере и при сбое питания
  нельзя считать штатной.
- **Проба «снять процесс и открыть снова» на свежем каталоге** — одна проверка
  в наборе. Зелёная остановка не доказывает, что база переживёт крестик.
- **Код «битый журнал — отложить и открыть заново» маскирует потерю данных.**
  Если он сработал, это событие, а не норма: журнал не удалять, разбирать.
  Прежде чем откладывать журнал, попробовать проиграть его иначе — через
  `ATTACH` из соединения в памяти; откладывать только то, что не проигрывается и так.
- В той же истории — **ложная «порча» журнала.** Узнавать повреждённый журнал по
  «wal» в тексте ошибки нельзя: DuckDB вписывает путь к файлу в ошибку замка.
  При папке `walnut` второй сервер отложил бы журнал работающего. Сначала узнать
  замок по подписи ошибки, потом — порчу.
