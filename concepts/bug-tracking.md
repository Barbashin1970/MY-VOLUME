# Баг-трекинг

**Система учёта найденных дефектов** с атрибутами, по которым принимается решение — когда чинить и в какой очерёдности.

## Главное различение: Severity vs Priority

| | Severity (серьёзность) | Priority (приоритет) |
|---|------------------------|----------------------|
| **Что отражает** | Техническая сложность бага | Угроза бага для бизнеса |
| **Кто назначает** | Тестировщик (механически) | PM / QA-lead (творчески) |
| **Шкала** | Абсолютная (C1-C5) | Относительная (High/Medium/Low) |
| **Меняется со временем** | Редко | Часто (релиз приближается → приоритет растёт) |

**Пример:** баг с **низкой серьёзностью** (опечатка в баннере «Чёрная пятница») может иметь **высокий приоритет** перед релизом — потому что висит на главной. И наоборот: критический сбой (high severity) в админке для одного пользователя — низкий приоритет.

## Шкала Severity (C1-C5)

| Уровень | Название | Когда |
|---------|----------|-------|
| **C1** | Blocker | Ни один элемент системы не работает: никто не может ей пользоваться |
| **C2** | Critical | Системный сбой / потеря данных / проблема с безопасностью |
| **C3** | Major | Система работает, но не так, как нужно. Элементы активны, но выполняют не то |
| **C4** | Minor | Функциональные проблемы. Работает, но неудобно. Дефект дизайна |
| **C5** | Trivial | Косметика. Не влияет на работу. Опечатка в тексте |

## Шкала Priority

| Уровень | Когда |
|---------|-------|
| **High (П1)** | Брось всё, чини. Showstopper — без него релиз не пойдёт |
| **Medium (П2)** | Не критично, но без починки ПО не будет работать как надо. SLA 72 часа |
| **Low (П3)** | Можно после критических. Зафиксировать до завершения релиза |

## Статусы тест-кейса

После сравнения ожидаемого результата (ОР) с фактическим (ФР):

| Статус | Когда | Что делать |
|--------|-------|-----------|
| **Passed** | ОР = ФР | Идти к следующему тест-кейсу |
| **Failed** | ОР ≠ ФР | Создать баг-репорт |
| **Known bug** | ОР ≠ ФР, но баг известен | Прикрепить ссылку на существующий баг-репорт |
| **Blocked** | Невозможно сравнить (мешает другой баг) | Прикрепить ссылку на блокирующий баг |
| **Skipped** | Не выполнили (нет предусловия / нет доступа / неактуально) | Объяснить, почему пропущено |

## Статусы баг-репорта

Жизненный цикл задачи в трекере (Redmine / Jira / GitHub Issues):

```
Not Assigned → Assigned → Fix in Progress → Fixed → Build in Progress →
Verify → Fix is Verified → Closed
                ↓
         Verification Failed → возврат к Fix in Progress
```

**Терминальные статусы (отказ):**
- `Can't Reproduce` — не воспроизвести (тестировщик должен перед заведением проверить второй раз).
- `Duplicate` — уже есть такой.
- `Not a bug` — это фича, тестировщик неверно понял спек.
- `3rd party bug` — баг во внешнем ПО, не нашей зоне.
- `No longer applicable` — устарело, неактуально.

## Атрибуты баг-репорта (обязательные)

| Поле | Что внутри |
|------|-----------|
| **ID** | Уникальный номер |
| **Заголовок** | «Что? Где? Когда?» — суть ФР |
| **Шаги воспроизведения** | Пошаговая инструкция |
| **Результаты** | ФР + ОР |
| **Окружение** | ОС, браузер, версия |
| **Severity** | C1-C5 |
| **Priority** | High/Medium/Low |
| **Статус** | На старте — Not Assigned |

**Необязательные:** описание, предусловие, постусловие, скриншоты, тип бага (баг / feature request).

## Применение в твоих проектах

| Проект | Где трекать |
|--------|-------------|
| **RAGRAF** | GitHub Issues в `~/RAGRAF` (соло). Severity + Priority в labels. |
| **LEYKA** | Аналогично. Для НГУ — можно дублировать в Redmine, если требуется заказчиком. |
| **POLINOM-JAVA** | GitHub Issues. Severity почти всегда C3-C4 (научный инструмент). |
| **GONKA / SOFIA** | GitHub Issues, упрощённо. Severity + Priority часто совпадают. |
| **AI-SKLAD / STROY** | Не нужен формальный трекер. Список в `BUGS.md` хватает. |

## Связь с ski-coding

В [ski-coding](../knowledge/skills/ski-coding.md) явного баг-трекера нет, потому что:
- Соло-режим: «нашёл — чини сразу или клади в backlog с **Почему**».
- BACKLOG.md как trackera-замена.
- Severity / Priority встроены: P0 = блокер, P1 = до конца итерации, P2 = в следующих итерациях.

**Соответствие:**

| Регламент QA | Ski-coding |
|--------------|------------|
| Severity C1-C2 | P0 (в audit-md) |
| Severity C3 + High priority | P1 (в audit-md) |
| Severity C4-C5 / Low priority | P2 (в BACKLOG.md с обоснованием) |

## Антипаттерны

❌ **Все баги High priority** — значит ни один не High. Должно быть ~10-20% High, остальное Medium/Low.

❌ **Не различать Severity и Priority** — критический баг в редко используемой функции откладывают, и наоборот.

❌ **Заводить баг без шагов воспроизведения** — программист его закроет как Can't Reproduce.

❌ **«Not a bug, it's a feature»** как часая отговорка — сигнал плохой документации (спек не покрыл случай).

❌ **Никогда не закрывать baglog'и как No longer applicable** — раздувание трекера, теряется фокус.
