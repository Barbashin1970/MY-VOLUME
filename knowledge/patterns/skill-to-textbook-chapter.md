# Skill из vault → глава учебника

**Паттерн.** Накопленный процедурный **skill** (пошаговый метод с принципами, фазами,
анти-паттернами) можно переиспользовать как **обучающую главу** продуктового учебника. Сохраняем
*глубокую структуру* метода, переписываем *поверхность* — кто действующие лица, какие артефакты,
какие примеры — под новую аудиторию.

> **⚠ Статус: кандидат (1-е применение).** По правилу раздела ([README](README.md) — «паттерн
> появляется на третьем применении») это пока **решение/наблюдение**, а не подтверждённый паттерн.
> Фиксирую как кандидат, чтобы поймать 2-й и 3-й случай. Плюс строго это приём
> *дидактики/управления знаниями*, а не архитектурный приём «выше фреймворка», как остальные в
> разделе, — возможно, со временем его место в `concepts/` или отдельной рубрике.

## Когда сработало (worked example)

`knowledge/skills/discovery-interview.md` написан как «**ИИ опрашивает Олега** перед стартом проекта
→ IDEA.md». Тот же метод лёг в **Главу 1.3 «Интервью со стейкхолдером»** учебника RAGRAF Flow DSL,
но в роли «**аналитик опрашивает стейкхолдера** → задача регламента + критерий решённости».

Перенеслось **без изменений** (глубокая структура):
- 5 принципов: один вопрос за раз · возражай, не стенографируй · боль раньше техники · тест мамы
  (прошлое, не гипотезы) · метки Известно / Предположил / Неизвестно;
- волновая структура (3 волны: контекст → задача+метрика → рамки);
- стоп-сигналы (3× «не знаю» → перенеси), анти-паттерн «пассивный стенограф».

Переписалось **под аудиторию** (поверхность):

| Слой | Skill (vault) | Глава учебника |
|---|---|---|
| Кто спрашивает | AI-агент | аналитик-методолог |
| Кого | Олег (founder) | стейкхолдер (диспетчер / прораб / ЛПР) |
| Артефакт на выходе | `inbox/IDEA.md` | черновик регламента + критерий |
| «Метрика работает» | бинарная метрика продукта | **критерий решённости** регламента |
| Пример | новый проект | диалог про ночной шум у школы (ШУМ-ИИ) |

## Почему переносится (глубокий enabler)

Оба контекста — частный случай одной задачи: **превратить размытое пожелание в задачу с проверяемым
критерием**. Пока «метрика работает / не работает» = «критерий решённости», метод элиситации один и
тот же. Ищи такую инвариантную сердцевину — она и есть то, что переносится. (Связь с задачным
подходом: критерий решённости — обязательный компонент задачи.)

## Рецепт переноса

1. Выдели в skill **инвариант** (принципы, фазы) и **контекст-специфику** (актёры, имена файлов,
   база предупреждений из конкретных проектов).
2. Инвариант — копируй; контекст — переписывай под новую аудиторию (термины, артефакты).
3. Замени внутренние примеры на **близкие новой аудитории** (бытовой/доменный диалог вместо
   «нового проекта Олега»).
4. Подложи **внешний авторитет** для доверия в публичном тексте: skill ссылался на приватный опыт —
   в учебнике добавь публичный источник (тест мамы, Rob Fitzpatrick) + честную оговорку, что
   волновая методика — внутренняя практика.
5. Сохрани канву главы учебника (Главное за минуту → … → ⚠ / 🎯), не «вали» skill как есть.

## Когда применять

- Есть зрелый skill/playbook, а нужна обучающая глава / онбординг на ту же тему.
- Внутренний метод хочется «отдать наружу» (клиентам, ученикам), не раскрывая приватную базу
  предупреждений и проектные эталоны.

## Анти-паттерны

- Скопировать skill дословно: останутся «ИИ-агент», `AskUserQuestion`, пути `inbox/` — для внешней
  аудитории это шум.
- Потерять инвариант: переписать «красиво», но выкинуть pushback / критерий — останется вежливая
  болтовня.
- Сослаться в публичном учебнике на приватный vault как на источник — лучше публичный аналог +
  оговорка.
