# Live-bound decision regulation

**Паттерн.** Регламент, который превращает живой поток данных (погода, пробки,
качество воздуха, дата) в один из N дискретных уровней — собирается из
**минимума блоков**: `входы → одна формула → switch по числовым границам →
выходы`. Без дублирующих формул-гейтов на каждый диапазон, без неиспользуемых
валидаций.

## Проблема, которую решает

В RAGRAF несколько «индексных» регламентов были собраны как:
- N формул-гейтов (по одной на диапазон), каждая заново пересчитывает индекс →
  «каша» из наезжающих узлов на диаграмме;
- десятки `threshold`/`SHACL`-цепочек для параметров, не влияющих на исход;
- **входы не привязаны к источникам данных** → формула считает на дефолтах →
  регламент всегда выдаёт «норму» (level 0). Признак: у входных нод нет
  входящих рёбер от sensor-нод и никто не подставляет значения.

## Решение

1. **Граф из минимума узлов.** `input × k → formula (1 шт.) → switch → output × N`.
   Switch маршрутизирует по **числовым границам кейса** `{value, label, min, max}`
   (`min ≤ V < max`) — ровно одна ветка, без формул-гейтов. (В RAGRAF это
   `_route_switch_by_bounds` в `flow_executor`; срабатывает, если у кейсов есть
   `min/max` и на входе switch — число от формулы.)

2. **Данные кормит ETL, а не sensor-ноды.** Если у регламента нет sensor-нод,
   `applier` не соберёт входы. Решение — отдельный коллектор, который читает
   снапшоты живого ETL и отдаёт значения **по `param_id`** (резолвится в input
   с тем же `paramRef`). Реестр коллекторов `regulation_id → collector`.

3. **Разделяй «эффективный вход» и «настраиваемый коэффициент».** Формула
   суммирует *эффективные* входы (их каждый прогон ставит applier). А
   **баллы/пороги/коэффициенты — это параметры регламента** (`referenceValue`),
   которые applier читает и применяет к сырым данным. Так аналитик докручивает
   «+/−» прямо в редакторе регламента, не трогая код. Чистая функция расчёта
   (`compute_*`) тестируется детерминированно, в отрыве от БД.

4. **Per-context связывание.** Снапшоты погоды/пробок/воздуха читаются по
   региону активного контекста (город); дата/время — по локальному часовому
   поясу контекста (а не UTC сервера). Это делает один регламент применимым к
   разным контекстам без правок.

## Когда применять

- Любой «индекс/уровень риска» поверх непрерывных метрик (0..N уровней).
- Когда нужна **объяснимость**: один граф = и модель, и визуализация, и
  документация; switch-границы видны и редактируемы.
- Когда базовая величина уже кодирует контекст (напр. уровень Яндекс-пробок
  кодирует сложность трасс города) — берём её базой, добавляем дельты → почти
  context-independent.

## Анти-паттерны (чего не делать)

- N формул-гейтов вместо switch-границ (дублирование расчёта + «каша»).
- Жёсткие магнитуды в коде вместо параметров регламента (не докрутить аналитику).
- Синтетический hand-coded оценщик, который `max()`-ит/перебивает результат flow
  — если flow самодостаточен, оценщик не нужен (ветка «нет оценщика → полагаемся
  на flow»).
- Входы без источника данных (мёртвый регламент, тихий level 0).

## Реализации в RAGRAF

- **nsk-traffic-forecast** — предиктивный индекс пробок: `Яндекс-база + прогноз
  погоды (Open-Meteo) + день/праздник → 6 уровней`. См. также
  `docs/FORECAST-SCENARIO-RAGRAF.md`.
- **nsk-mobile-index** — транспортные выбросы по измеряемому воздуху:
  `NO₂ + PM2.5 − рассеивание ветром → 4 уровня`.
