# Пирамида тестирования

**Базовая модель распределения автотестов** по объёму, скорости выполнения и стоимости поддержки. Сформулирована Майком Коном (2009), стала индустриальным стандартом.

> Главная идея: **низкоуровневых тестов больше, высокоуровневых — меньше**. Не наоборот.

## Структура

```
                  ┌─────────┐
                  │ Ручные  │   ← дороже всего, дольше всего
                  └─────────┘
              ┌─────────────────┐
              │  E2E / UI-тесты │
              └─────────────────┘
          ┌─────────────────────────┐
          │ Интеграционные тесты    │
          └─────────────────────────┘
     ┌─────────────────────────────────────┐
     │       Юнит-тесты                    │   ← быстрые, дешёвые
     └─────────────────────────────────────┘
                                                 ────────►
                                              Количество тестов
```

## 4 уровня

| Уровень | Что проверяет | Скорость | Стоимость поддержки | Доля от общего объёма |
|---------|---------------|----------|---------------------|----------------------|
| **Юнит-тесты** | Отдельная функция / класс | Миллисекунды | Низкая | 70-80% |
| **Интеграционные** | Взаимодействие двух модулей (например, DB + API) | Секунды | Средняя | 15-20% |
| **E2E (end-to-end)** | Сценарий целиком — от UI до БД | Минуты | Высокая (хрупкие) | 5-10% |
| **Ручные** | Что не автоматизируется (UX, accessibility, исследовательское) | Часы | Очень высокая | Минимум |

## Главные правила

### 1. Юнит-тесты должны быть **изолированы**

- Не зависят от других тестов.
- Не зависят от внешних ресурсов (БД, сеть, файлы).
- Можно запускать в любом порядке — не ломаются.

Зависимости разрываются через **моки** (имитация поведения) и **стабы** (имитация состояния).

### 2. Правило атомарности

Хороший тест **нельзя декомпозировать** на несколько маленьких. Один тест — одна проверка.

### 3. Code coverage — не самоцель

100% покрытие **не означает** «все сценарии протестированы». Инструменты coverage (Jacoco для Java, coverage.py для Python) считают, какие строки кода выполнились. Они **не знают**, осмысленные ли данные были на входе.

Минимально приемлемый порог обычно 80%. Выше — диминишинг.

### 4. Чем выше тест в пирамиде, тем дороже его поддержка

E2E-тесты:
- Хрупкие — ломаются от изменения вёрстки.
- Долгие — минуты на прогон.
- Сложные в отладке — упал, а где именно?

Если в проекте больше E2E, чем юнит — это **анти-паттерн «мороженое»** (перевёрнутая пирамида). Сигнал, что архитектура плохо тестируема.

## Параметризация

Когда тесты отличаются только данными — применяй параметризацию (`@pytest.mark.parametrize`, JUnit `@ParameterizedTest`). Один метод, разные входы — поддерживать в разы дешевле.

## Связь с ski-coding

В [ski-coding](../knowledge/skills/ski-coding.md) шаг 6 (тесты) — **каждой фазе свой юнит-тест**. Это значит, пирамида строится **снизу вверх параллельно с разработкой**, а не «потом, после релиза».

## Антипаттерны

❌ **«Мороженое»** (перевёрнутая пирамида) — много E2E, мало юнит. Сигнал плохой архитектуры (модули не изолированы).

❌ **«Песочные часы»** — много юнит + много E2E, мало интеграционных. Промежуточный слой пропускает баги интеграции.

❌ **100% coverage как KPI** — приводит к тестам, написанным ради coverage, а не ради смысла.

❌ **Юнит-тесты, которые ходят в БД** — это уже интеграционные. Юнит должен быть изолирован.
