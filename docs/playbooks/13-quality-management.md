## Часть I — Главный принцип

> **Качество планируется с этапа идеи.** Не «сначала пишем, потом тестируем», а «понимаем, как будем тестировать — и поэтому проектируем именно так».

Это означает: **QA-стадия начинается раньше кода**. На стадии 1 (IDEA) уже думаем, какие критерии качества будем мерить. На стадии 4 (ТЗ) уже понимаем, какие сценарии будем тест-кейсить. На стадии 5 (архитектура) уже закладываем тестируемость.

## Часть IV — Главное отличие для соло-режима: ski-coding

Классический QA-регламент опирается на разделение ролей:

```
PM пишет спек → программист пишет код → QA пишет тест-кейсы
        ↓                ↓                       ↓
   PRD / SRS         юнит-тесты              баг-репорт
```

В соло-режиме с LLM ролей нет. Их заменяет **чередование текстовых и кодовых шагов** — [ski-coding](../../knowledge/skills/ski-coding.md):

```
аудит (текст) → реализация (код) → актуализация docs (текст) →
UI-фичи (код) → backlog (текст) → тесты (код) → следующий аудит
```

Это **компактификация** классических 5 стадий QA до 6 повторяющихся шагов, ни один из которых нельзя пропустить.

### Соответствие 5 ↔ 6

| 5 стадий QA | Шаги ski-coding |
|-------------|-----------------|
| Test Analysis (ЧТО) | Шаг 1: аудит-md (`<TOPIC>-AUDIT.md`) |
| Test Design (КАК) | Шаги 1 + 3: аудит + актуализация ARCHITECTURE/SKILL |
| Test Execution | Шаг 6: phase-tests |
| Test Automation | Шаг 6 + DevOps pipeline (Jenkins/GitHub Actions) |
| QA Monitoring | Self-Aware Reporting (§6 ski-coding) + ретроспектива каждые 5-7 итераций |

## Часть VI — Конкретные практики, которые внедрить из регламента

### VI.1 На стадии 4 (ТЗ ГОСТ-19) добавить раздел «Критерии качества»

Из регламента — **чек-лист критериев качества спека**:

- Акцент на деталях и их чёткое определение.
- Забота о недопущении неверного толкования.
- Непротиворечивость внутри спека и с другими спеками.
- Логическая взаимосвязь компонентов.
- Полнота охвата предмета.
- Соответствие нормативным актам.
- Соответствие деловой практике.

Это **прямо в шаблон ТЗ** — см. [04-tz-and-gost-19](04-tz-and-gost-19.md).

### VI.2 На стадии 5 (архитектура) — раздел «Тест-стратегия»

В `ARC.md` добавить §-раздел:
- Что тестируется юнит-тестами (см. [test-pyramid](../../concepts/test-pyramid.md)).
- Что — интеграционными.
- Что — E2E.
- Какой target по code coverage (обычно 80%).
- Какие техники тест-дизайна применяются ([test-design-techniques](../../concepts/test-design-techniques.md)).

### VI.3 На стадии 6 (SKILL-NN-*) — отдельный SKILL-TESTING.md

В каждом проекте категории A — отдельный документ:
- Виды автотестов (юнит / integration / E2E).
- Параметризация (JUnit / pytest.parametrize).
- Использование моков и стабов.
- Правило атомарности и изоляции.
- Что в pre-commit hooks.

Эталон — `~/RAGRAF/docs/SKILL-SKICODING.md` §7 + [ski-coding §4.2](../../knowledge/skills/ski-coding.md) (критерий «фаза готова»).

### VI.4 На стадии 7 (комплект ГОСТ-19) — раздел «Программа и методика испытаний»

Это **уже есть в ГОСТ 19.301** — теперь у нас есть шаблон содержания:
- Объект испытаний.
- Цель испытаний.
- Программа испытаний — функциональные тест-кейсы.
- Методика — пошаговое описание каждой проверки.
- См. [gost-19](../../concepts/gost-19.md).

### VI.5 На стадии 9 (charter + reports) — раздел «Метрики качества»

В отчёте за период:
- **Баг-рейтинг** = баг-репорты / 1000 строк кода.
- **Ревью-рейтинг кода** = баги, найденные на код-ревью.
- **Ревью-рейтинг юнит-тестов** = баги в юнит-тестах.
- **Ревью-рейтинг документации** = баги в спеках / макетах / архитектуре.

Динамика этих метрик показывает зрелость процесса.

## Часть VII — Тестирование как DevSecOps

Безопасность — часть качества. См. [ski-coding §6](../../knowledge/skills/ski-coding.md) (security checklist):

1. **Секреты:** `.env`, `.duckdb`, `credentials.json` в `.gitignore`.
2. **Constant-time сравнения:** `hmac.compare_digest`, не `==` для токенов.
3. **Cookies:** `httponly=True, secure=True, samesite="lax"`.
4. **Admin endpoints:** через `Depends(require_admin)`.
5. **Pre-commit hooks:** падают — чиним причину, не `--no-verify`.

Виды тестов безопасности из регламента: XSS, XSRF/CSRF, обход авторизации, DoS/DDoS.

## Часть VIII — CI/CD как стандарт для категории A

См. [ci-cd](../../concepts/ci-cd.md).

**Стек по умолчанию** (соответствует [ADR-001](../decisions/adr-001-default-stack.md)):
- **Git** — общий репозиторий.
- **GitHub Actions** (предпочтительно) или Jenkins — CI/CD pipeline.
- **Docker** — контейнеризация окружений.
- **Kubernetes** — если масштаб требует (LEYKA-Enterprise, RAGRAF многоконтурный).

Pipeline-минимум для категории A:
1. Push в feature-ветку → автозапуск юнит-тестов.
2. Pull request → линт + type-check + интеграционные тесты.
3. Merge в main → деплой на staging + smoke-тест.
4. Tag release → деплой на production.

## Часть IX — Применение в твоих проектах

### LEYKA / RAGRAF (категория A)

- Полный QA-цикл по плейбуку.
- CI/CD через GitHub Actions.
- Ski-coding как ежедневная практика.
- В ARC.md §13 («Тест-стратегия») — заполнен.
- В отчётах для НГУ — метрики качества за период.

### GONKA / SOFIA / KNIFFEL (категория B)

- Юнит-тесты основной логики + ручной smoke перед деплоем.
- Ski-coding в усечённом виде: шаги 1+2+6 (без актуализации docs и backlog в отдельных артефактах).
- В README.md — раздел «Тестирование» с инструкцией для контрибуторов.

### POLINOM / POLINOM-JAVA / NSK (категория C)

- JMH-метрики обязательны (POLINOM-JAVA).
- Юнит-тесты алгоритмических ядер.
- Тест-план как часть НИР-отчёта.
- Ski-coding фазами «эксперимент» вместо «sprint».

### AI-SKLAD / STROY / demo-sigma (категория D)

- Smoke перед отправкой клиенту.
- Чек-лист «работает на основном сценарии демо».
- Не более.

## Часть X — Чек-лист «качество в проекте»

В конце каждого спринта / итерации:

- [ ] Юнит-тесты основной логики написаны и проходят?
- [ ] Code coverage ≥ выбранного порога (по умолчанию 80% для категории A)?
- [ ] CI pipeline зелёный?
- [ ] Smoke-тест на staging прошёл?
- [ ] Pre-commit hooks включены (нет обхода `--no-verify`)?
- [ ] `.gitignore` закрывает секреты?
- [ ] Аудит-документ последней итерации актуален?
- [ ] Backlog содержит `Почему` для каждой deferred-фазы?
- [ ] Документация (ARC, SKILL, README) синхронна с кодом?
- [ ] Self-Aware Reporting — статусы full/partial/planned проставлены?

Если 3+ галки не проставлены — следующая итерация начинается **с ретроспективы**.
