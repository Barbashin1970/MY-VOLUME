# Урок: «сплошной rewrite = весь сайт отвечает 200»

> Контекст: БЕРИМАЖ, витрина косметики на Vercel. Пришло письмо: сайт не
> настроен на возврат 404. Конфиг при этом был ровно тот, который советует
> предыдущий урок этого же vault'а — и он был правильным ровно до того дня,
> когда сайт начали индексировать.

## Что произошло

Проверка живого сайта одной командой:

```
/net-takoy-stranicy-12345   → 200
/kniga/net-takoy-glavy      → 200
/catalog/lico/lishnee       → 200
```

Во всех трёх случаях отдавалась главная страница. Ни одного 404 сайт не
умел возвращать в принципе.

## Почему это случилось

Две причины в двух разных слоях, и обе выглядят как правильный код.

**1. Сервер.** `vercel.json` содержал канонический для SPA рецепт:

```json
{ "source": "/(.*)", "destination": "/index.html" }
```

Он обязателен, пока задача — «чтобы прямые ссылки открывались». Но
буквально он значит «любой адрес существует», и другого прочтения у него
нет. Поисковик, получив 200 и содержимое главной, записывает страницу как
существующую: это и называется **soft 404**. Последствия не косметические —
робот тратит бюджет обхода на мусорные адреса, а переименованная страница
остаётся в индексе живой навсегда, потому что старый адрес продолжает
честно отвечать 200.

**2. Приложение.** В роутере стояло то же самое, написанное руками:

```jsx
<Route path="*" element={<Navigate to="/" replace />} />
```

Переброс на главную ощущается заботой («не показывать человеку тупик»), а
работает как обман: ссылка вроде открылась, но не то. И для робота, который
выполняет скрипты, это второй источник того же сигнала.

Важно: **это не баг, это устаревшее решение.** Сплошной rewrite был верен
на этапе «сайт должен открываться» и стал вреден на этапе «сайт должен
индексироваться». Условие сменилось молча.

## Как починили

Три слоя, каждый закрывает свой случай.

**1. Точечные правила вместо шаблона.** По правилу на маршрут витрины и
одно на всю админку:

```json
{ "trailingSlash": false,
  "rewrites": [
    { "source": "/podbor",        "destination": "/index.html" },
    { "source": "/catalog/:slug", "destination": "/index.html" },
    { "source": "/product/:id",   "destination": "/index.html" },
    { "source": "/admin/:path*",  "destination": "/index.html" }
  ] }
```

**2. `404.html` в корне сборки.** Соглашение Vercel: файл с таким именем
отдаётся со статусом 404, когда не подошёл ни файл, ни правило. Отдельной
настройки не требует. У страницы должен стоять `noindex` и **не должно
быть** canonical: канонический адрес значит «вот настоящая страница вместо
этой», а настоящей не существует.

**3. Экран «страницы нет» в приложении** вместо `Navigate` — для переходов
внутри SPA, где HTTP-статуса нет вовсе. Тексты у него и у `404.html` общие,
за совпадением следит тест.

Порядок маршрутизации у Vercel, на котором всё держится:
**redirects → файловая система → rewrites → 404.html.** Предрендеренные
страницы выигрывают у правил, потому что они файлы; мусор доезжает до
конца и получает 404.

## Чтобы не повторилось

**Правило 1. Сплошной rewrite — временная мера, а не финальная
конфигурация.** Он нужен, чтобы сайт заработал. Перед тем как отдавать
сайт роботу (карта сайта, панель вебмастера, первый внешний линк) — заменить
на точечные правила. Это отдельный пункт чеклиста стадии «публикация», а не
то, что вспомнится само.

**Правило 2. Проверять обе стороны, а не одну.** Половина проверки ловит
половину бед:

```bash
S=https://site.example
# несуществующее обязано отдавать 404
for p in /net-takoy /razdel/net-takogo /wp-login.php; do
  printf "%-28s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' "$S$p")"
done
# и каждый адрес из карты сайта обязан отдавать 200
curl -s "$S/sitemap.xml" | grep -o '<loc>[^<]*' | cut -c6- \
  | xargs -P8 -I{} sh -c 'printf "%s %s\n" "$(curl -s -o /dev/null -w "%{http_code}" "{}")" "{}"' \
  | grep -v '^200'
```

Вторая половина не декоративная: точечные правила легко забыть на одном
маршруте, и сломается он **только на проде** — локальный dev-сервер отдаёт
приложение по любому адресу.

**Правило 3. Косая черта на конце — переадресация, а не 404.** Правила
пишутся без неё, и `/podbor/` не подходит ни под одно. Это не «страницы
нет» — так адрес пишут в письмах и так его нормализуют некоторые роботы.
`"trailingSlash": false` заставляет Vercel отвечать 308 на канонический вид
и заодно сводит оба написания к одному адресу в выдаче. **Проверил на
живом сайте после первой правки — и поймал именно это.**

**Правило 4. Список маршрутов, продублированный в конфиг, обязан иметь
сторожа.** Цена точечных правил — маршрут, добавленный в роутер и забытый
в `vercel.json`. Тест, который читает оба файла и сверяет, стоит двадцати
минут:

- вытащить `path="..."` из роутера;
- превратить `source` из `vercel.json` в регулярку (`:name` → один сегмент,
  `:name*` → ноль и больше);
- проверить, что каждый маршрут покрыт **и** что заведомо чужой адрес не
  покрыт ничем — это ловит возвращение сплошного шаблона.

**Правило 5. Шаг сборки, от которого зависит существование страниц, обязан
ронять сборку.** Предрендер книги раньше при отсутствии исходников писал
предупреждение и продолжал: с сплошным rewrite сайт всё равно работал.
После перехода на точечные правила тот же пропуск означал бы 30 адресов из
карты сайта, отвечающих 404. Общее: **как только что-то становится
несущим, его мягкая деградация превращается в тихую катастрофу** — ищи
такие места при каждой смене архитектуры.

**Правило 6. Переброс на главную — это не «дружелюбно», это ложь.** Для
неизвестного адреса рисуй страницу «такого адреса нет» со ссылками на
разделы. Человек поймёт, что произошло; робот получит `noindex`.

**Правило 7. Google не пингуется.** Его адрес для пинга карт сайта
отключён с 2023 года (проверено 2026-09-09: отвечает 404), IndexNow он не
поддерживает. Автоматизировать можно только Яндекс и Bing — через IndexNow,
без аккаунта, по ключу-файлу в корне сайта. Для Google остаётся Search
Console руками.
