# Урок: «мутация прошла, экран остался прежним»

> Контекст: АРХИ, страница стройпортфеля. Владелец нажал «Обновить», обход
> Plan-R прошёл за полминуты, огонёк в полосе состояния позеленел — а числа
> на странице остались двухдневными, и в перечне снимков верхним по-прежнему
> стоял позавчерашний. Перезагрузка страницы всё чинила.
>
> **Третий проект подряд.** До этого — LEYKA и РАГРАФ, другой стек, та же
> беда. Поэтому урок здесь, а не в проектной папке.

## Что произошло

1. Человек нажимает кнопку, запускающую изменение данных (подкачка, импорт,
   пересчёт — неважно).
2. Действие честно отрабатывает: сервер отвечает, в базе новые строки.
3. **Экран показывает прежнее.** Ни числа, ни списки не меняются.
4. `F5` — и всё на месте.

Коварство в том, что **что-то на экране всё-таки обновляется**. В АРХИ полоса
состояния опрашивает сервер сама и себя же перерисовывает: огонёк зеленеет,
давность сбрасывается на «5 мин назад». Страница выглядит живой — и тем
убедительнее лжёт: рядом со свежим огоньком стоят позавчерашние числа.

Два прочтения у пользователя, и оба плохие:

* «кнопка не работает» — жмёт ещё раз, и ещё;
* «данные и правда двухдневные» — и это уже не про интерфейс, а про решения,
  принятые по устаревшим числам.

## Почему это случилось

**Данные читаются один раз, при открытии страницы.** Дальше никто не обязан
узнавать, что они сменились.

Формулировка, к которой всё сводится и которая не зависит от стека:

> **Тот, кто узнаёт о смене данных, обязан об этом объявить. Тот, кто рисует,
> обязан уметь перерисоваться.** Если эти двое не знакомы — экран устаревает
> молча.

В React с TanStack Query это ловится само собой — ровно до тех пор, пока
кто-то не забудет `invalidateQueries` в `onSuccess`: библиотека не
догадывается, какие запросы испортила ваша мутация. В ванильном JS
догадываться некому в принципе, и дыра открыта по умолчанию.

**Второй случай той же беды — без всякой кнопки.** Страница открыта, фоновая
задача (планировщик, вебхук, соседняя вкладка) обновила данные — и открытая
страница молча показывает прошлое. Здесь нет ни мутации, ни `onSuccess`,
цепляться не за что. Поэтому ключ инвалидации — **не «нажали кнопку», а
«данные стали другими»**.

## Как починили

Один объявляющий, много слушающих. В АРХИ объявляет полоса состояния
(`web/obshchee.js`) — она и так опрашивает сервер каждые 20 секунд и первой
узнаёт новости:

```js
function smenilis_dannye(z) {
    var teper = { snimok: String(z.snimok_id) + "|" + (z.snimok_konec || ""),
                  idet: !!z.idet_opros };
    var bylo = proshloe;
    proshloe = teper;
    if (bylo === null) { return false; }          // первый ответ — не смена
    return teper.snimok !== bylo.snimok           // удачный обход
        || (bylo.idet && !teper.idet);            // обход кончился отказом
}
// …
if (smenilis_dannye(z)) {
    window.dispatchEvent(new CustomEvent("arhi:dannye-obnovilis", { detail: z }));
}
```

Страница подписывается и перечитывает себя **своим же загрузчиком**:

```js
function zagruzitDannye() {
  return pokazatSnimok().then(pokazatPortfel).then(pokazatPorucheniya)/* … */;
}
zagruzitDannye();
window.addEventListener("arhi:dannye-obnovilis", zagruzitDannye);
```

Четыре решения внутри этого фикса, каждое стоило отдельного раздумья:

**Признаков смены два, не один.** Номер снимка ловит удачный обход; «обход
кончился» — неудачный. Неудачный снимка не создаёт, но строку в журнале
оставляет, и на административной странице она нужна не меньше удачной.

**Первый ответ сменой не считается.** Страница только что загрузилась
сама — объявить ей смену значит заставить перечитать всё дважды, на каждом
открытии.

**Перерисовываются не все виды, а зависящие от данных.** Таблицу настроек
с полями ввода трогать нельзя: фоновая задача сотрёт то, что человек
набирает прямо сейчас. От опроса настройки не меняются — перечитывать нечего,
а терять есть что.

**Условие, без которого всё это не работает:** каждый загрузчик обязан сперва
чистить своё гнездо и лишь потом рисовать. Проверьте это перед тем, как
опираться, — иначе повторный вызов удвоит содержимое вместо обновления.

## Чтобы не повторилось

**Правило 1. Ключ инвалидации — состояние данных, а не факт нажатия.**
Версия, `updated_at`, номер снимка, ETag — что угодно, что меняется вместе
с данными. Тогда одно и то же решение закрывает и кнопку, и планировщика,
и соседнюю вкладку. Привязка к `onSuccess` закрывает только кнопку.

**Правило 2. `location.reload()` — не лечение.** Строка вместо архитектуры,
и цена видна сразу: теряется прокрутка, закрываются раскрытые разделы,
пропадает набранный в полях текст, мигает вся страница. Перерисовка своими
загрузчиками стоит десяти строк и не стоит ничего пользователю.

**Правило 3. В React проверять `invalidateQueries` при код-ревью любой
мутации.** Вопрос ревьюера дословно: *«какие запросы эта мутация испортила
и где они инвалидируются?»* Ответ «данные обновятся при следующем заходе»
означает баг.

**Правило 4. Симптом ставит диагноз.** «Помогает F5» = данные читаются один
раз, и никто не сообщает об их смене. Не надо искать в коде мутации —
искать надо подписку, которой нет.

**Правило 5. Ищите обманчиво живой элемент.** Если на экране есть что-то
самообновляющееся — часы, индикатор связи, счётчик, — беда выглядит
безобиднее, чем она есть: страница кажется живой. Это же и подсказка, где
брать объявляющего: он уже написан и уже опрашивает сервер.

**Правило 6. Это тестируется без браузера.** Настоящий файл поллера
исполняется узлом с подставленным окружением и поддельным сервером, время
под управлением теста: `setTimeout` кладёт задачу в очередь, тест вызывает
её сам. Проверять четыре случая:

| Что подаётся | Чего ждём |
|---|---|
| открытие → действие → новые данные | ровно одно объявление |
| первый ответ сервера | молчание |
| N одинаковых ответов подряд | молчание |
| действие кончилось отказом | объявление (в журнале появилась строка) |

Плюс статическая проверка: каждая страница с данными **слушает** событие.
Объявление без слушателя выглядит работающим и не работает.

> Подделывая DOM для такого теста, помните: `getElementById`, возвращающий
> узел на любой вопрос, убеждает код, что он уже всё построил. В АРХИ на этом
> потерялось полчаса — поллер решал, что панель создана, и не начинал опрос.
