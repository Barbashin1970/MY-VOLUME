# Урок: время из SQLite без пояса браузер читает как местное

## Что произошло

LEYKA, пользователи в Новосибирске (UTC+7). Ссылка-приглашение, созданная в 16:17,
на своей странице обещала действовать «до 09:17» следующей недели. Разбор показал
то же у всех отметок времени. Комментарий, написанный в 16:17, стоял в ленте
с меткой 09:17, а «N ч назад» в «Сообщениях» врало на 7 часов.

Ответ API был таким:

```
"expires_at": "2026-10-17T09:17:27.269563"     ← ни «Z», ни «+07:00»
```

## Почему это случилось

Три звена, и каждое по отдельности «правильное»:

1. **Бэкенд пишет UTC.** `default=lambda: datetime.now(timezone.utc)`.
2. **SQLite пояс не хранит.** Колонка `DateTime(timezone=True)` на SQLite
   возвращает naive datetime: компоненты UTC без пометки, что это UTC.
   Pydantic сериализует naive как есть, без смещения. На Postgres
   с `timestamptz` пояс вернулся бы сам, поэтому смена базы молча меняет
   формат API.
3. **Браузер читает строку без пояса как местное время.** По ECMAScript строка
   дата-время без смещения — местное время, а строка «только дата»
   (`2026-10-17`) — UTC. `new Date("2026-10-17T09:17:27")` в Новосибирске
   означает 09:17 по Новосибирску, то есть 02:17 UTC.

Итог: каждый момент уезжает назад на смещение пользователя. В UTC+7 это заметно
сразу, в Москве (+3) не так бросается в глаза, в Лондоне не видно вовсе.

## Как починили

**На границе, в схеме ответа, а не в базе.** Тип в `app/schemas/utc.py`:

```python
def _as_utc(value: datetime) -> datetime:
    return value if value.tzinfo else value.replace(tzinfo=timezone.utc)

UtcDatetime = Annotated[datetime, AfterValidator(_as_utc)]
```

Поля-моменты в схемах ответов объявлены как `UtcDatetime` и уходят
с «Z». Сравнения дат на сервере и хранение не тронуты, миграция не нужна.
Фронт не менялся: `new Date("…Z")` переводит момент в местное время сам.

**Не всё время — момент.** Опись нашла 45 datetime-полей в схемах. 34 из них
моменты: `created_at`, `updated_at`, `changed_at`, `edited_at`, `generated_at`,
`expires_at`, границы кварталов. 11 календарные: `due_date`, `occurred_at`.
Календарную дату выбрал человек, и хранится она «настенным» временем. Если дать
ей «Z», срок «до 18:00» в UTC+7 станет 01:00 следующего дня. Календарные поля
оставлены без пояса: браузер читает их как местные, и это верно.

**Моменты — все разом.** Лента задачи сортирует комментарии и историю статусов
сравнением строк (`a.ts.localeCompare(b.ts)`). Пояс у одного поля без другого
перемешал бы ленту.

**Сторож.** Проверка обходит все схемы `app/schemas/*` и требует, чтобы у каждого
datetime-поля был объявлен вид: момент (`UtcDatetime`) или имя из списка
календарных. Падает и на моменте без пояса, и на календарном поле с поясом.
На откаченных схемах она назвала поимённо все 30 непереведённых полей.

## Чтобы не повторилось

- **Для каждого поля со временем решить: момент или календарная дата.**
  Момент — когда что-то случилось («создано», «изменено», «истекает»). Календарная
  дата — то, что человек выбрал в календаре («срок», «дата события»). Момент
  отдаётся с поясом, дата — без пояса или как `date`.
- **Лечить на границе.** Схема ответа — единственное место, где время уходит
  наружу. Тип колонки в ORM меняет сравнения дат во всём бэкенде, и на это нужна
  отдельная итерация.
- **Ставить сторожа на решение, а не на поле.** Проверка «у каждого
  datetime-поля объявлен вид» ловит следующее поле, которого сегодня нет.
- **Проверить внешних читателей API.** Здесь это РАГРАФ: его `_parse_iso`
  принимает и «Z», и время без пояса, и совместим. Клиент, который вычитает
  aware из naive, упал бы на `TypeError`.
- **Показ и расчёт — разные беды.** Показ починен, но сервер по-прежнему считает
  «сегодня» и кварталы по UTC. В первые семь часов квартала по Новосибирску он
  думает, что квартал ещё прошлый. Это записано в бэклог LEYKA отдельной темой.
- **Быстрая проба на любом проекте с SQLite:**
  `curl -s <api>/<что-то с created_at> | grep -o '"created_at":"[^"]*"'`.
  Нет «Z» или смещения — браузер уже показывает чужое время.
