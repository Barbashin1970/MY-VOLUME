# Техники тест-дизайна

**Как генерировать сценарии и данные для тестов** так, чтобы покрыть требования и не делать бесконечного количества проверок. 4 техники для **создания** тестов + 2 для **отбора**.

## 5 правил тест-дизайна

1. На одно требование может быть несколько тест-кейсов.
2. Один тест-кейс — одна проверка.
3. Проверки не должны дублироваться.
4. Проверки — в рамках требований (нет тестов «телефон в жидком азоте», если спек не описывает).
5. Проверки должны покрывать все требования.

Когда все требования покрыты и нет дубликатов — **definition of done**.

## Часть I — Техники создания (4 метода)

### 1. Черновик → чистовик

**Этап «черновик»** (`dirty list`): без анализа, отдавшись фантазии, накидать ВСЕ идеи. Локальный мозговой штурм. Вопросы команде, идеи, сценарии — даже самые «не из этой оперы».

**Этап «чистовик»**: проанализировать, оставить жизнеспособное, сгруппировать (позитивные / негативные / по функциональностям). На основе чистовика — тест-кейсы.

**Когда применять:** в начале тест-анализа, когда не понятно, с чего начать.

### 2. Матричная раскладка тестовых данных

Для конкретного поля ввода (или параметра) построить таблицу: элементы → значения.

**Пример: поле «почтовый индекс» (6 цифр)**

| Условие | Значения |
|---------|---------|
| Индекс введён? | Да / Нет |
| Действующий? | Да / Нет |
| Сколько и каких символов? | 5 / 6 / 7 цифр; буквы; пробелы |

**Комбинации:**
- Позитивные: 6 цифр + действующий (630117)
- Негативные: 6 цифр + 000000 / 5 цифр / 7 цифр / буква О вместо нуля / пробел внутри / пустой ввод

**Когда применять:** для каждого поля ввода, особенно с валидацией.

### 3. Блок-схемы

Для сложных юнитов и интеграций — визуализировать логику процесса. Блок-схема даёт идеи:
- Где есть условие → нужны тесты обеих веток.
- Где есть цикл → нужны тесты «0 итераций / 1 итерация / много».
- Где есть параллельные потоки → нужны тесты гонки.

**Когда применять:** для бизнес-логики со сложным потоком (заказ оплачен → склад → доставка).

### 4. Техника туров

Способ спроектировать **исследовательское тестирование**. Тестировщик выбирает фокус и проходит ПО в разных «срезах»:

| Тур | На что смотреть |
|-----|-----------------|
| **По функциональности** | Пройдись по продукту. Что делает каждая фича? |
| **Перемен** | Где пользователь может менять данные? Какие ограничения? |
| **Сложности** | Самые запутанные места — там копятся баги |
| **Взаимодействия** | Как разные части общаются? |
| **Пользователей** | Несколько персон. Что важно каждой? |
| **Структуры** | Из чего состоит? UI / API / БД / файлы? |
| **По данным** | Какие данные принимает / хранит / передаёт? |

**Когда применять:** для исследовательского тестирования (когда спека нет или продукт незнаком).

## Часть II — Техники отбора (2 метода)

### 5. Классы эквивалентности

**Эквивалентный класс** = множество значений, к которым ПО применяет одинаковую логику. Тестируем **по одному** значению из каждого класса — этого достаточно.

**Пример: возраст пользователя**

| Класс | Логика |
|-------|--------|
| < 14 лет | Запрет регистрации |
| 14-17 лет | Регистрация с согласием родителей |
| 18-64 года | Полная регистрация |
| 65+ лет | Полная регистрация + спец-предложения |

Тестируем 4 значения, например 10 / 16 / 30 / 70 — этого достаточно для покрытия логики.

### 6. Граничные значения

**Баги живут на границах классов.** Для каждого класса проверяем 5 точек:

**Позитивные (внутри класса):**
- Нижний предел.
- Верхний предел.
- Любое значение в середине.

**Негативные (за границами):**
- Верхний предел предыдущего класса (если есть).
- Нижний предел следующего класса (если есть).

**Пример для класса «18-64 года»:**
- 17 — нижняя граница предыдущего класса (должно отвергнуться или попасть в другой класс).
- 18 — нижняя граница.
- 30 — середина.
- 64 — верхняя граница.
- 65 — нижняя граница следующего класса.

### Оптимизация: дедупликация

Пограничные значения часто повторяются (64 ↔ 65 общая граница двух классов). Не дублировать в тестах.

## Сочетание методов 1 + 2 + 3

Лучший результат даёт **комбо**:
- Черновик → накидать сценарии.
- Матричная раскладка → конкретные данные.
- Блок-схемы → не пропустить условия.

## Применение в твоих проектах

| Проект | Техника |
|--------|---------|
| **RAGRAF** | Блок-схемы потока (flow.json → validator → executor → metrics). Каждый узел = вход в матричную раскладку (Pydantic-поля). Тестируется через `test_flow_executor.py`. |
| **LEYKA** | Матричная раскладка для КОСГУ-категоризации (тип задачи × проект × статус → код КОСГУ). Граничные значения для дат отчётного периода (31.12 vs 01.01). |
| **AI-SKLAD** | Матричная раскладка форматов CSV (с/без BOM, разные разделители). Туры по сценариям пользователя (загрузка → анализ → отчёт). |
| **POLINOM** | Классы эквивалентности по сложности входа (n=10, n=100, n=10000) + JMH-бенчмарки на границах. |
| **GONKA / KNIFFEL** | Туры (исследовательское тестирование) — формальных тест-кейсов почти нет. |

## Антипаттерны

❌ **Только позитивные тесты** — негатив находит больше багов. Обязательно проверять, как система реагирует на невалидный ввод.

❌ **Тестировать «всё подряд»** — не успеешь. Без классов эквивалентности количество комбинаций взрывается.

❌ **Не тестировать границы** — там 70% багов. Off-by-one — классика.

❌ **Туры без фокуса** — без формулировки «что ищем» исследование размазывается.

❌ **Пропустить черновик и сразу писать чистовик** — теряются неожиданные идеи.
