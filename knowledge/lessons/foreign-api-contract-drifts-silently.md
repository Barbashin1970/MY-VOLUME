# Урок: «интеграция работала, только ничего не делала»

> Контекст: РАГРАФ ↔ LEYKA. Выход регламента может завести задачу в трекере,
> а критерий решённости «задача закрыта в срок» потом спрашивает LEYKA о её
> статусе. Клиент LEYKA в РАГРАФ хранит базовый адрес вместе с версией —
> `…/api/v1` (`backend/app/config.py:98`).

## Что произошло

**Случай 1 — двойной префикс.** До 04.09.2026 в двух местах путь был записан
полностью, `/api/tasks`: создание задачи (`leyka_task_creator.py`) и проверка
статуса (`etl/acceptance_resolver.py`). Запрос уходил на `/api/v1/api/tasks`,
LEYKA отвечала 404. Задача автоматически не заводилась, критерий «задача закрыта
в срок» не мог выполниться никогда — а в интерфейсе не было ни одной ошибки:
сбой уходил в журнал процесса.

**Случай 2 — параметр, которого никто не ждёт.** Ручка РАГРАФ
`GET /api/leyka/tasks?status=…` передаёт в LEYKA параметр `status`
(`backend/app/api/leyka.py:349–352`), а LEYKA принимает `status_filter`
(`~/LEYKA/backend/app/api/v1/tasks.py:63`). Неизвестный параметр запроса FastAPI
не отвергает, а молча игнорирует: ответ 200 и полный список вместо отфильтрованного.

## Почему это случилось

- **Адрес собирается из двух половин, и каждая половина «правильная».** Базовый
  адрес с версией и абсолютный путь с `/api` порознь выглядят нормально;
  неправильна только склейка, а её никто не проверял.
- **Отказ чужой системы не доходит до того, кто ждёт результат.** 404 при
  создании задачи — строка в журнале процесса; на экране регламента —
  «ожидает», вечно.
- **Фреймворки щедры к лишнему.** Неизвестный параметр запроса не ошибка
  ни для FastAPI, ни для большинства веб-фреймворков, поэтому опечатка
  в договоре выглядит как работающий вызов.
- **Договор проверяли на подставной LEYKA,** собранной по нашему же пониманию
  её API, — подставка разделяет нашу ошибку.

## Как починили

- Случай 1 — 04.09.2026: пути переписаны относительно базового адреса
  (`/tasks`), в обоих местах оставлен комментарий «ФИКС 2026-09-04»
  (`leyka_task_creator.py:82–83`, `acceptance_resolver.py:115–116`).
- Случай 2 — на 30.10.2026 не починен; найден сверкой исходников обеих систем
  при подготовке книги и заведён в бэклог вместе с соседними расхождениями
  (задача без обязательного `project_id`, обязательная `position` при смене
  статуса).
- Пакет проверок «боевой» — договор с чужой действующей системой, запускается
  только явно — механизмом в РАГРАФ есть, а проверок в нём пока нет ни одной.

## Чем обнаружено

Ни одной проверкой. Случай 2 — чтением кода двух систем рядом (30.10.2026).

## Чтобы не повторилось

- **URL к чужой системе собирает одно место,** и на каждый вызов есть проверка
  «итоговый адрес такой-то» — склейку проверяют, а не половины.
- **Фильтр проверяют тем, что он фильтрует:** запросили `done` — в ответе только
  `done`. Ответ 200 ничего не доказывает.
- **Сбой чужой системы виден там, где ждут результат:** статус интеграции
  на экране, запись в журнале доставок или задач, а не только
  `logger.exception`.
- **Договор подтверждает проба против живой системы,** в отдельном пакете
  с явным запуском. Пока такой пробы нет, договор — гипотеза. Подставка
  по собственному пониманию чужого API подтверждает только это понимание.
